# Runbook: как обрабатывается репозиторий кольца

Стандарт для любого репозитория-участника Zen Pool. Задача runbook'а — чтобы репозиторий читался как
обычный инженерный проект: понятные имена, описания, история без горы одинаковых прогонов.

## Что обязательно в репозитории кольца

| Пункт | Что именно | Кто/чем |
|---|---|---|
| Имя воркфлоу | человеческий `name:` в `.github/workflows/zen-pool.yml`, например `Zen Pool — inference worker` | `ring-hygiene --rename-workflows` (после провижининга) |
| Описания входов | у каждого `workflow_dispatch`-входа — `description:` | файл-источник воркера |
| README | назначение репозитория: что обслуживает, как устроен, что за пул | репозиторий кольца |
| Структура | `worker/`, `scripts/`, `MODELS.md`, `SETUP.md` — как у обычного проекта | репозиторий кольца |
| Чистота Actions | завершённые прогоны старше `keep_hours` удалены | `ring-hygiene` (cron + ручной запуск) |
| Права токена | Actions включены, `default_workflow_permissions: read` | `ring-hygiene --harden` |

## Что НЕ делать (сломает кольцо)

- **Не переименовывать файл воркфлоу** `zen-pool.yml` — кольцо адресует воркфлоу по имени файла.
  Меняется только строка `name:` (отображаемое имя), и только ею.
- **Не менять рабочие скрипты** (`zen-pool-worker.mjs`, `zen-client.mjs`) в рамках «приведения вида» —
  это отдельная задача с прогоном живого вызова.
- **Не удалять и не подменять содержимое** репозитория ради внешнего вида: репозиторий должен
  выглядеть нормально потому, что он такой и есть, а не потому что внутрь положили чужой проект.
- **Не печатать токены**: per-repo токены читаются из реестра в рантайме CI и маскируются `add-mask`.

## Порядок работ

1. `zen-ring-sync` (mode=register, provision=true) — разложить воркер по кольцу.
2. `ring-hygiene` (dry_run=true) — отчёт: сколько прогонов старше `keep_hours`, что изменится.
3. `ring-hygiene` (реальный прогон) — удалить старое, выставить read-only токен, дать имя.
4. Проверка: `/zen/pool/health` — живые воркеры на месте; живой вызов (`zen-pool-call`) отвечает.

`zen-ring-sync` сам вызывает шаг «readable workflow names» после провижининга, поэтому имя не
откатывается при следующей раскладке.

## Что копится и почему

Прогоны копятся потому, что каждый воркер — это run GitHub Actions, а пул периодически поднимает
новые. REST API не даёт ни массового удаления (`DELETE /actions/runs?created=` → 404), ни настройки
срока хранения (`actions/permissions/retention` → 404), поэтому `ring-hygiene` удаляет прогоны по
одному (`DELETE /actions/runs/{id}`) и делает это по расписанию.
