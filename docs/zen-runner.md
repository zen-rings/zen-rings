# Zen Runner — контролер запуска тестов свободных моделей

Дата: 4 октября 2026. Живёт в том же воркере, что и лестница: `https://llm-ladder.trainedassist.store`.

## Зачем он нужен

Самотест бил по каждой бесплатной модели на каждом прогоне. Провайдер, который лежит часами,
получал 22 одинаковых `500` подряд — и это никого не останавливало. Вторая проблема: счётчики
жили внутри одного процесса, а GitHub Actions каждый раз даёт свежую машину, поэтому между
прогонами лимиты и паузы обнулялись.

Оба ограничения живут теперь в базе, а не в памяти воркера.

## Что он делает

1. **Карантин с экспоненциальным отступом.** Модель, которая три раза подряд ответила одной и
   той же «серьёзной» ошибкой, уходит в тишину: 30 мин → 2 ч → 6 ч → 24 ч. Квота и таймаут
   тишины не покупают — их проверяем снова через минуту.
2. **Лимиты 50 в минуту и 500 в сутки** на пару (репозиторий, модель). Настоящая квота zen считается
   на пару (IP, модель), а репозиторий — это ровно один исходящий адрес, поэтому несколько
   репозиториев в кольце = во столько же раз больше бюджета. Плюс общий тормоз по провайдеру.
3. **Круговая очередь по репозиториям.** Каждый запуск уходит в следующий включённый репозиторий его
   собственным токеном — это и есть умножение бюджета.
4. **Модель не выбирается здесь.** Назвал модель вызывающий — значит, дохлая бесплатная модель
   никогда не будет молча заменена на платную (инцидент #86).

## Контракт

Все маршруты — под собственным токеном `ZEN_RUNNER_TOKEN`, до ворот лестницы, поэтому путь
`/v1/chat/completions` не затронут.

| Маршрут | Что делает |
|---|---|
| `GET /zen/health` | живость, размер реестра, число моделей, текущие капы — без токена |
| `GET /zen/models` | таблица: модель, статус, `verdict: run \| skip`, `next_check_in`, последняя ошибка |
| `POST /zen/run` | `{model, runs?}` → `202 {run_id, repo, location, ring_size}` |
| `POST /zen/report` | `{run_id?, model, ok, kind?, error?}` → состояние, которое читает `/zen/models` |
| `POST /zen/repos` | строка реестра: репозиторий + зашифрованный токен — **только `ZEN_RING_ADMIN_TOKEN`** |
| `GET /zen/ring/repos` | реестр как есть, без токенов (тот же админский токен) |
| `GET /zen/ring/payload` | тот же список **с** открытыми токенами, расшифровка в воркере, `no-store` |

Отказы всегда явные:

| Ответ | Значение |
|---|---|
| `202` | запуск принят и ушёл в GitHub |
| `400` | не задана модель (контроллер её не выбирает) или модель не похожа на id |
| `401` | неверный токен вызывающего |
| `409 {retry_after}` | модель в карантине, вот когда вернёмся к ней |
| `429 {retry_after}` | упёрлись в 50/мин или 500/день |
| `502 {gh_status}` | GitHub отказал в запуске |
| `503` | контролер не настроен (нет токена/репозитория/ключа) |

## Как модель попадает в состояние

Состояние learns только из отчётов. Самотест после прогона шлёт `POST /zen/report` по каждой
модели (`ok`, `kind`, `error`). Без этого таблица остаётся пустой, каждая модель выглядит
«неизвестной» — и именно так дохлый провайдер получает по 100 запросов за прогон.

Виды отказа (`kind` — из классификации клиента):

| `kind` | Что означает | Решение |
|---|---|---|
| `ok` | ответила | счётчики сброшены, следующая проверка через 6 ч |
| `provider`, `rate`, `daily`, `timeout` | квота или таймаут | `flaky`, проверка через минуту, лестница не растёт |
| `error`, `fingerprint` | провайдер/model сломаны | 3 одинаковых подряд → `down` и лестница отступов |

Замер, на котором это построено (4 октября, 13:38–13:42 МСК, `zen-runner/probe-2026-10-04.md`):
`jev-1.13-free` — 22 одинаковых `500` из 22; `fledge-alpha-free` — 2 успеха из 22 (~9%);
контрольная `nemotron-3-ultra-free` — 10 из 10, то есть все красные ответы пришли от провайдера.

## Реестр репозиториев

`POST /zen/repos` — одна строка на репозиторий:

```json
{ "repo": "vovalikessmoothy-png/LLM-test", "token": "github_pat_…", "location": "" }
{ "repo": "vovalikessmoothy-png/ai-agent-runs-pool", "token_ref": "env:GITHUB_AI_AGENT_RUNS_POOL" }
```

- `token` шифруется AES-GCM ключом `ZEN_TOKEN_KEY` и никогда не возвращается и не пишется в лог;
  без ключа контролер отказывается принимать токен, а не хранит его открытым.
- `token_ref: "env:NAME"` ссылается на токен, который уже лежит в секрете воркера — так его не надо
  записывать второй раз.
- `{"repo": …, "enabled": false}` гасит строку, не удаляя её.
- В принимающем репозитории должен быть триггер `repository_dispatch: types: [zen-run]`.

### Реестр и есть источник правды (5 октября 2026)

Раньше список кольца жил в секрете GitHub `ZEN_RING_PAYLOAD`, а его наполнял агент по таблице
владельца. Схема ломалась в двух местах: таблицу и секрет могли развести, и без агента правки
владельца не доезжали никуда. Сейчас единственная копия — таблица `zen_repos` в D1 этого же воркера,
и её читает то, что реально работает:

| Кто | Что читает | Чем |
|---|---|---|
| воркер (диспатч в кольцо) | `zen_repos` | напрямую из D1 |
| `zen-ring-sync.yml` | `GET /zen/ring/payload` | `ZEN_RING_ADMIN_TOKEN` |
| владелец | `scripts/zen-ring.mjs list\|add\|disable` | `ZEN_RING_ADMIN_TOKEN` |

Два токена намеренно разные. `ZEN_RUNNER_TOKEN` — низкий: он лежит в секретах **каждого** члена
кольца (вызвать модель, отчитаться). `ZEN_RING_ADMIN_TOKEN` не уезжает ни в одно кольцо: он открывает
реестр на запись и список с открытыми токенами. Один токен на обе задачи означал бы, что
скомпрометированный публичный участник кольца читает PAT всех приватных репозиториев.

Два правила, которые нельзя нарушать:

- строка `env:NAME` возвращается из payload **вместе** с `resolved_token`, но назад пишется только
  ссылка — иначе `env:`-строка превратится в замороженную копию секрета, который должен
  ротироваться; поэтому шаг provision берёт `.token // .resolved_token`, а шаг register шлёт
  `token_ref` без `token`;
- этот репозиторий публичный: логи и inputs Actions читает кто угодно. Токен из payload маскируется
  (`::add-mask::`) до того, как что-либо сможет его напечатать, и никогда не передаётся аргументом.

Переезд был разовым: `zen-ring-sync` с `source: gh-secret, import: true` перелил строки секрета в
D1 (воркер зашифровал их своим `ZEN_TOKEN_KEY`), после чего `source: cf` стал умолчанием, а секрет
`ZEN_RING_PAYLOAD` удалён.

## Проверка

```bash
# живо, без токена
curl -fsS https://llm-ladder.trainedassist.store/zen/health

# таблица (нужен ZEN_RUNNER_TOKEN)
curl -fsS -H "authorization: Bearer $ZEN_RUNNER_TOKEN" \
  https://llm-ladder.trainedassist.store/zen/models

# кольцо — состав без токенов (нужен ZEN_RING_ADMIN_TOKEN)
curl -fsS -H "authorization: Bearer $ZEN_RING_ADMIN_TOKEN" \
  https://llm-ladder.trainedassist.store/zen/ring/repos | jq -c '.repos[]|{repo,enabled,token_ref,has_token}'

# запуск теста модели
curl -fsS -X POST -H "authorization: Bearer $ZEN_RUNNER_TOKEN" -H 'content-type: application/json' \
  -d '{"model":"qwen3-235b-a22b-thinking-2507-free","runs":2}' \
  https://llm-ladder.trainedassist.store/zen/run
```

Юнит-тесты контроллера: `node --test test/zen-runner.test.js` (11 тестов: лестница отступов,
классификация отказов, лимиты, кольцо, шифрование токена, все маршруты).

# Zen Pool — долгоживущий раннер как API (4 октября 2026)

## Зачем

Один диспатч = один ответ платит полный холодный старт (~10–13 замерено) на каждый вызов.
Zen Pool поднимает **один** раннер, регистрирует его у нас и держит открытый длинный опрос:
вызывающий шлёт задачу и получает ответ в том же HTTP-запросе. Замер живого прогона
(5/5 PASS): быстрый путь **2,7–2,9 с** против 10–13 с на холодный диспатч, и тот же job
обслуживает второй запрос без перезапуска.

## Сторож вызывающего

`wait_ms` — сколько вызывающий готов ждать ответ. По умолчанию **30 с** (число владельца),
зажимается в `[1 с, 90 с]`; потолок 90 с — это idle-таймаут края, дольше ответ забирается
по `GET /zen/pool/result/{task_id}`. Таймаут не теряет работу: задача остаётся в очереди,
ответ приходит и забирается по `task_id`.

## Карантин и явный вызов

Карантин отвечает на вопрос «надо ли **пробивать** модель по расписанию», а не «вызывающий
назвал её явно». Поэтому `POST /zen/pool/invoke` карантин **не** проверяет: успех по модели
больше не уводит пул в тишину на 6 ч и не блокирует второй вызов. Защита на этом пути —
бюджет 50/мин и 500/сутки.

## Автоскейлер (потолок 20, резерв 2, TTL 167 мин)

Аккаунт держит 20 одновременных job'ов, поэтому пул ограничен сверху, а два слота остаются
свободными для обычного CI — наши воркеры не должны вытеснять сборки.

| Параметр | Значение | Как менять |
|---|---|---|
| потолок | 20 | `ZEN_POOL_CEILING` |
| резерв | 2 | `ZEN_POOL_RESERVE` |
| TTL воркера | 167 мин | `ZEN_POOL_TTL_MS` |
| окно λ | 5 мин | `LAMBDA_WINDOW_MS` в коде |
| время обслуживания τ | 10 с | `ZEN_POOL_SERVICE_MS` |
| окно загрузки | 25 с | `BOOT_MS` в коде |
| выключить | — | `ZEN_POOL_AUTOSCALE=off` |

Решение о размере пула — две правила по порядку:

1. **Ф8**: непустая очередь масштабирует вверх сразу — минимум на одного воркера больше, чем
   есть. Холодный пул отвечает на реальный вызов, а не отдаёт 503: задача ставится в очередь,
   воркер загружается, а сторож вызывающего покрывает ~10–13 с загрузки.
2. **Закон Литтла** `N = λ·τ` — при устойчивом λ пул разгоняется до нужного размера без очереди.

Резерв — это запас под потолком, а не с пола: один холодный вызов поднимает одного воркера,
а не трёх. Пустая очередь не масштабирует — воркеры сами выходят по TTL.

### Маршруты пула

| Маршрут | Что делает |
|---|---|
| `GET /zen/pool/health` | живые воркеры, очередь, потолок/резерв/TTL — без токена |
| `GET /zen/pool/metrics` | λ, очередь, live, inflight, desired, `toDispatch`, причина, последние диспатчи |
| `POST /zen/pool/scale` | `{demand?}` → прогнать автоскейлер сейчас (200 с планом, 503 если нечем грузить) |
| `POST /zen/pool/invoke` | `{model, prompt, max_tokens?, wait_ms?}` → ответ в том же запросе; на холодном пуле сам поднимает воркер (`cold_start` в ответе) |
| `POST /zen/pool/register` / `GET /zen/pool/pull` / `POST /zen/pool/result` / `POST /zen/pool/stop` | сторона job'а: регистрация, длинный опрос, ответ, выход |
| `GET /zen/pool/result/{task_id}` | ответ в любой момент, в том числе после 504 |

### Кто запускает автоскейлер

- `POST /zen/pool/invoke` — по факту вызова (Ф8, без ожидания расписания);
- `.github/workflows/zen-pool-scale.yml` — cron каждые 2 минуты: читает `metrics` и диспатчит
  `zen-pool.yml` в **своём** репозитории. Каждый член кольца может добавить себя в пул, поэтому
  потолок — свойство кольца, а не одного репозитория. Требует `actions: write` и секрет
  `ZEN_RUNNER_TOKEN`.

## Проверка пула

```bash
# живость и размер пула (без токена)
curl -fsS https://llm-ladder.trainedassist.store/zen/pool/health

# решение автоскейлера (нужен ZEN_RUNNER_TOKEN)
curl -fsS -H "authorization: Bearer $ZEN_RUNNER_TOKEN" \
  https://llm-ladder.trainedassist.store/zen/pool/metrics

# один вызов — ответ в том же запросе
curl -fsS -X POST -H "authorization: Bearer $ZEN_RUNNER_TOKEN" -H 'content-type: application/json' \
  -d '{"model":"nemotron-3.5-lightning-free","prompt":"2+4?"}' \
  https://llm-ladder.trainedassist.store/zen/pool/invoke
```
